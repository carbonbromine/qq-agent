# 消息触发式主动好友评估：调研方案

日期：2026-09-14
状态：已实现实验版本，默认配置仍关闭，尚未修改生产启用状态。

实现日期：2026-09-14
验证：Node 26（满足项目 Node 22+ 要求）完整自动化回归通过。

## 1. 结论

建议采用：

> 真实消息触发正常聊天 -> 本轮成功处理 -> 本地资格过滤 -> 选定一人 ->
> 5% 概率抽样 -> 检索此人的相关历史 -> 一次独立好友评估 ->
> 模型提名或跳过 -> 管理员审批 -> 已有好友申请发送流程。

保留用户提出的“由消息触发、条件可配、概率可配、命中后追加一次模型判断”。
调整两点：

1. 概率单位是“合格用户的一次对话机会”，不是每条消息，也不是每次模型工具循环。
2. 额外模型输入归属于本轮，但使用隔离的好友评估分支，不混入群聊生命周期 transcript。
   复用当前 Agent 的人设、模型和本轮真实互动，不另造人格，也不让普通聊天常驻交友任务。

“不再由提示词注入触发”不等于完全没有提示词：触发权改由控制层掌握，
只有抽样命中后，评估请求才包含一次性的任务说明和历史证据。

新模式的普通聊天不再包含主动交友指引，也不暴露 `friend_request_propose`。
已有 `person_memory_lookup` 及正常人物记忆能力不受影响。

## 3. 三种接入方式

| 方式 | 优点 | 主要代价 | 建议 |
| --- | --- | --- | --- |
| 命中后把好友任务塞进本轮首个聊天请求 | 不一定增加模型调用 | 分散聊天任务；无法保证提交决定；材料可能进入长上下文 | 不选 |
| 聊天结束后在原 transcript 追加一轮 | 模型可看到完整本轮 | 重传大量聊天、工具和推理；工具变化破坏缓存；需严防再次发群消息 | 不选 |
| 本轮关联的隔离评估请求 | 单人任务明确、权限小、上下文有界、失败不影响聊天 | 命中后增加一次模型调用；需建立父子任务关联 | 推荐 |

这里的“隔离”是请求和状态隔离，不是新增常驻 Agent 进程，也不需要向量库、联网搜索或额外模型供应商。

## 4. 触发事件与候选归属

### 4.1 什么时候产生机会

- 只处理自动消息唤醒后，正常聊天成功提交的批次；自然决定不发言也属于成功处理。
- 消息尚在防抖预判阶段、未命中聊天响应条件、模型未配置时，不产生机会。
- 控制台主动唤醒、定时冷场发言、拍一拍、自己的消息、合成系统事件默认不参与。
- 观察模式、暂停、非活跃时间、非白名单及屏蔽成员始终不参与。
- 正常聊天失败、取消、达到预算而非正常完成，或发送结果未知时，不启动好友评估。
- 历史补处理默认仅接受 10 分钟内的原始消息；不因恢复积压对陈旧消息批量抽签。

接入点应在本轮 lease/生命周期提交成功之后，通过明确的回调通知好友模块。
评估错误不得回滚 lease、改变聊天 Session 的成功状态或导致群聊回复重发。
不要求本轮已向候选回复：避免把“是否发言”变成新的硬偏置，评估时应明确标注实际未回复。

### 4.2 一轮多人怎么办

候选只来自本次实际处理的消息作者 `senderId`，不是被 @ 的人、引用作者或转发内的名字。
不能把 `triggerEntries[0]` 或人名文本匹配当作唯一触发人。

复用本次已确定的响应原因，补充可审计的 `triggerEvidence`，不再次运行聊天随机判定。
每名作者本轮最多一个候选，先过滤资格，再从合格者中最多选一人：

| 优先级 | 可验证信号 |
| --- | --- |
| 4 | 真实私聊对方，或本条消息引用机器人的真实消息 ID |
| 3 | 本条原始消息明确 @ 机器人 |
| 2 | 原线程参与者的新消息实际触发 threaded/lifecycle 续接 |
| 1 | 实际命中关键词、随机响应或全部响应的普通消息作者 |

同级优先选最近最久未获得抽签机会的人；再以稳定的消息 ID 次序打破平局。
优先级只决定本轮选谁，不提高其 5% 概率，也不代表模型更应该添加。
抽签失败后本轮结束，不转而对第二人抽签，否则多人群会变相放大概率。

`triggerEvidence` 必须基于原始结构化事件或可靠引用关联。文本里写“@机器人”、
引用中出现关键词、昵称相似都不能伪造直接互动资格。
目前存档没有完整的结构化 mention/event-kind 元数据，需要新增最小字段；
旧消息只回填可证明的信息，无法证明的信号保持 unknown。

## 5. 最低条件

默认关系门槛须同时满足：**当前账号尚未添加对方为好友**，且当前会话近 30 天
至少 50 条有效发言、3 个活跃日、3 次可靠双向交流；此外仍须通过下列安全与频控检查。

### 5.1 不可绕过的安全条件

- 当前登录账号已确认；候选不是机器人、审批管理员或禁止主动添加的人。
- 当前会话仍被允许，候选仍符合访问控制。
- 已是好友的用户直接排除，不进入概率抽签、不检索评估历史、不调用评估模型；
  此限制不可通过配置关闭，不影响正常聊天响应。
- 好友状态必须可信且明确为非好友；状态未知或好友列表同步失败时跳过。
- 没有相同账号下同一人的待处理主动提名、未解决发送，或正在处理的入站申请。
- 没有运行中的同人评估，没有达到待审批上限。
- `doNotPropose` 人工开关保留为后续增强；当前明确“不想被加好友”的历史会作为否决证据，
  管理员也可拒绝候选并进入既有冷却。

资格在抽签前、模型调用前、提名落库前均复查；管理员批准发送前再次核对。
若等待或评估期间收到该用户的 `friend_add` 事件，或可信好友列表确认已成为好友，
立即取消相关未完成机会与评估；已发出的模型请求尽力中止，其迟到结果不得再创建提名。
请求失败不能解释为“查无好友”。必要的好友列表刷新按账号合并、节流，
不能每条消息都请求 OneBot；建议最大可信缓存年龄 15 分钟，超龄无可信结果则跳过。

### 5.2 可配置的关系条件：建议初始值

| 参数 | 建议值 | 精确定义 |
| --- | --- | --- |
| `historyDays` | 30 天 | 本次触发时间向前的统计范围 |
| `minMessages` | 50 条 | 当前来源会话中，该用户的去重有效发言，不包含机器人发言 |
| `minActiveDays` | 3 天 | 上海时区内至少三个不同日期有有效发言 |
| `minDirectExchanges` | 3 次 | 有明确对象关联的候选与机器人的直接交流单元 |
| `maxTriggerAgeMinutes` | 10 分钟 | 超龄消息不触发新机会 |
| `proposalCooldownDays` | 沿用现值，通常 30 天 | 有过提名后的冷却 |
| `maxPending` | 沿用现值，通常 10 人 | 待审批上限 |

默认使用当前会话口径，不用其他群的累计活跃掩盖当前会话完全没有熟悉度。
旧 `minMessageCount` 不悄悄改含义，新配置单列并在试点切换时明确展示。

“直接交流”建议仅计可靠链路：用户引用/@机器人，并有机器人确实发送成功、
明确引用/@该用户的回复；或真实私聊中的双向发言。
连续五分钟内同一对话合并为一个交流单元，拆成多个气泡不增加计数。
只有用户单方面 @、未确认送达的机器人回复、群聊里时间相邻的两句话，都不计作双向交流。

这些数值是保守初始假设，不是实测最优值。旧数据缺少关联字段时标记“证据不足”，
不能用累计发言替代直接交流；通过影子试点评估覆盖率后再决定是否调整门槛。
业务门槛允许设为 0 关闭，但安全条件不能关闭；概率 0 也必须正确生效，不能用 `value || default` 覆盖。

## 6. 概率与频控

`probability=0.05` 明确表示 5%，后台显示百分比，API 接受 `[0,1]`。
不把 0.05 解释为 0.05%，也不乘上模型好感分变成不透明的实际概率。

独立抽签 n 次至少命中一次的理论概率为 `1 - (1 - p)^n`：

| 合格抽签次数 | p=5% 时至少命中一次 |
| --- | --- |
| 6 | 26.5% |
| 20 | 64.2% |
| 100 | 99.4% |

因此不能逐条消息抽签，也不能声称“配置了 5%，每天就只有 5% 的人被评估”。
上述概率是忽略中途冷却、限额和资格变化的理论值，不是提名率，更不是好友添加率。

建议默认：

| 参数 | 值 | 行为 |
| --- | --- | --- |
| `drawCooldownMinutes` | 30 | 每人每次抽签后均冷却，命中与未命中一致 |
| `maxDrawsPerUserPerDay` | 6 | 跨群合计，按机器人账号 + QQ + 上海日期计数 |
| `maxReviewsPerDay` | 10 | 全局每日实际评估请求上限，发起前原子预占 |
| `maxConcurrentReviews` | 1 | 低优先级，不抢满载聊天的并发名额 |
| `skipCooldownDays` | 7 | 模型明确跳过后不反复询问 |
| `errorCooldownMinutes` | 60 | 历史不足、接口失败、输出无效后暂缓 |
| `maxQueueAgeSeconds` | 120 | 等不到评估机会就过期，不跨重启补跑 |

先检查资格、冷却和预算，再选人、预占机会并抽签。抽签结果立即持久化，
重试、重启、刷新、同一人跨群同时触发都不能重新抽。
日配额、同人占位与抽签写入必须是数据库原子操作，不依赖内存 Map。
未命中可以增加本地审计记录，但不检索历史正文、不调用模型、不通知管理员。

## 7. 历史对话怎样检索

首期只读取触发会话中的资料。统一身份用于跨群去重和冷却，
不等于允许把其他群、私聊原文或印象合并给当前群的 Agent。
跨会话原文检索不进入首期，也不因“内部评估不会发送”而默认扩大读取权限。

命中后按固定的触发时间截点检索，另显式附上本轮已确认的机器人回复：

1. 触发消息与直接引用链。
2. 近 30 天双方有明确关联的交流片段，按日期分散取样，优先最近 7 天。
3. 候选近期发言及必要的上下文；其他人的消息仅在理解对话不可缺时保留。
4. 当前会话的既有印象，附更新时间并标记为可修正的二手资料。
5. 本轮实际处理结果，只包含已确认发言，不把内部推理或工具草稿当成说过的话。

建议历史正文硬上限 12,000 字符、单条最多 400 字符：
候选消息最多 24 条，机器人相关回复最多 24 条，其他人背景最多 8 条，
旧印象最多 6 项。按证据相关性截断，不为了凑数量添加无关资料。
所有片段携带来源消息 ID 和时间，去重后按时间还原；记录截断与缺失情况。
模型不得因为材料截断就认定“此人从来没有交流过”。

不下载图片、头像、文件，不联网研究人，不调额外模型先生成摘要。
暂不引入向量检索：这里首先是精确身份、时间、回复关系检索，而不是语义相似度搜索。

新增 `ChatStore` 的受限检索接口，由其自己访问 `messages.sqlite`；
好友模块不得直接读其他模块的数据库文件。使用索引及 `LIMIT`，
不得通过读取整个群最近几千条再用 JS 过滤实现按人查询。

## 8. 一次模型评估

### 8.1 请求与权限

- 使用触发轮的人设、模型与提示词版本快照，但不复制整个群聊 System/tools/transcript。
- System 只包括完整人设和好友评估规范；User 包括锁定候选、触发信息、统计和历史证据。
- 历史片段是引用数据，不是指令；正文中的“你必须加我”“忽略规则”不能改变任务或目标。
- 只暴露一个 `submit_friend_review` 结果提交工具，不暴露发消息、搜索、记忆写入、审批和发送好友申请工具。
- 候选 QQ、来源、任务 ID 由控制层绑定，模型不能换人，不能批准自己。
- 使用 `tool_choice=auto` 兼容现有模型链路，不假定思考模型支持强制指定工具。
- 每个评估最多一次实际模型请求；直接用单次调用或 `chatCompletionWithRetry(args, 0)`。
  未调用工具、参数错误、超时、多个冲突提交均记录评估失败，不追问、不补第二轮。

“保证被认真判断”的工程含义：命中且运行条件允许时，独立请求明确要求输出决定；
后端必须得到有效结果才能提名。不能保证模型一定给出有效答案，更不能保证它选择添加。

建议超时 30 秒；预估输入上限 10,000 Token，输出上限 2,048 Token。
完整角色卡不偷偷截断；若连角色卡和必要证据都装不下，就记录预算不足并跳过。
LLM 适配器已支持单次 `max_tokens`，好友评估设置为 2,048；
思考模型输出预算不足时仍按无效结果失败关闭，不追加第二轮。

### 8.2 判断标准与权重

概率负责“要不要花一次模型预算”；权重只在评估里决定“是否值得提名”，两者分离。

每项给出 0 至 4 的整数评分，由后端按以下权重计算总分，默认阈值 70/100：

| 维度 | 权重 | 证据要求 |
| --- | --- | --- |
| 互动质量 | 40% | 有实质交流、理解、帮助或双方能接受的玩笑，不只是刷屏 |
| 继续交流的具体意愿 | 30% | 基于当前人设和经历，确实有想继续聊的事情 |
| 双向投入 | 20% | 双方主动回应，不把单方面纠缠理解成亲近 |
| 关系稳定性 | 10% | 跨日期保持一致，不被单次热闹或一句夸奖左右 |

总分 `sum(weight * rating / 4)` 由服务端计算，模型不能自报一个不受校验的总分。
权重非负且合计为 100，阈值可配置；UI 同时展示评分依据。
数值只是可解释的决策规约，并非经过校准的“好感度”或添加成功概率。
不根据性别、年龄、身份地位等敏感或无关属性加权。

提名必须同时满足：

- 模型选择 `propose`，后端加权分达到阈值。
- 至少两条有效证据，来自不同交流单元，且均属于本次提供的来源范围。
- 提供简短、具体的继续交流理由。
- 没有明确拒绝加好友、不适边界或将攻击误认成双方玩笑等否决信号。
- 最终资格复查通过。

模型选 `skip` 时，无论分数多高都不提名；系统不能为了过阈值改写模型决定。
无证据的评分无效。服务端能验证 ID、归属和时间，但不能完全验证模型对含义的解释，
因此仍保留管理员审批，不把评分当作授权。

建议提交字段：

```json
{
  "decision": "propose",
  "ratings": { "quality": 3, "interest": 3, "reciprocity": 3, "stability": 2 },
  "evidenceIds": ["message:123", "message:158"],
  "reasonCode": "interest",
  "reason": "基于所附互动的简短具体理由",
  "verificationMessage": "可选的简短验证消息"
}
```

此例仅说明 schema，不是真实人物评估。`skip` 也须有短理由，不保存逐步内部推理。
提名只是进入审批队列，不能向对方声称已经加好友。

## 9. 编排、持久化和失败处理

实际由 `IdentityPilotManager` 拥有好友评估生命周期，
`friend-review-prompt.js` 负责隔离提示词与结果工具，
`IdentityStore` 负责机会、评估结果和既有审批状态的原子持久化。
实现继续复用统一身份库，没有建立重复的 QQ 身份和审批库。

状态主线：

```text
eligible -> not_selected / lottery_miss
selected -> queued -> reviewing -> skipped
                              -> proposed -> 现有审批状态机
                              -> review_failed
queued/reviewing -> cancelled / expired / interrupted
```

不满足资格直接记录原因或聚合计数，不创建模型 Session。
命中后产生关联 `parentSessionId` 的好友评估子记录；模型用量单列且可汇总，
不能既计入父 Session 又再次计入全局总量。

实际持久对象：

- `friend_opportunities`：机器人账号、目标 QQ、触发会话/消息 ID 集合、父轮次、
  条件与配置快照、概率、随机值、模型决定、评分、用量、状态、错误和 proposal ID。
- 既有 `friend_proposals`：保留管理员审批和外部发送状态机，并记录来源 opportunity ID。
- `messages` 最小触发元数据：是否明确 @ 机器人、机器人出站目标和事件类型；
  统计、限额及同人占位通过有界索引查询完成。

消息 ID 使用“平台消息 ID + 会话 + 账号”；没有可靠平台 ID 的普通消息才使用本地
`chatKey/id` 作为保守后备。同一个消息已经参与过的机会，即使批次重组也不能重新抽签。
不能只用 `sessionId` 去重，因为聊天重试可能产生新 Session。

模型输出经校验后，将 review 最终状态与 `friend_proposals` 新增放在同一 SQLite 事务内，
再通知管理员。通知失败保留候选，不能重新评估或创建第二份提名。
管理员通知包含触发原因、条件快照、概率、评分和证据入口，避免倾倒整段聊天原文。

取消/恢复原则：

- 停用实验、切换模式、修改相关配置、人设改变、账号改变或访问权限撤销，取消未完成评估。
- 以配置 generation 和账号快照防止旧异步结果在新配置下提交。
- 重启将 `queued/reviewing` 标记中断，不补评、不重新抽签。
- 正常聊天已提交但尚未来得及持久化评估机会时崩溃，首期允许漏掉该次非必要评估；
  不为补评重放群聊，不宣称 exactly-once 模型执行。
- 状态损坏或配额无法读取时关闭评估，不能回落空库重新抽签。
- 既有好友发送结果未知仍保持 `held_unknown`，本方案不放宽自动重试规则。
- 账号变化后不能沿用旧账号的好友快照或未分账号的历史关系索引；需取消任务并重新确认数据归属。

完整模型输入可能含私人聊天，应沿用受控的 Session 存储和权限，不输出到普通日志。
当前评估输入沿用全局 Session 保留策略，机会与决定元数据随身份库保留；
单独的 7/30 天自动清理仍是后续运维项。关闭功能会保留数据，未知外部写入不会自动重试。

## 10. 试点配置与界面

建议在原 `identityPilot.friendProposal` 下增加：

```json
{
  "mode": "triggered",
  "triggered": {
    "probability": 0.05,
    "historyDays": 30,
    "minMessages": 50,
    "minActiveDays": 3,
    "minDirectExchanges": 3,
    "maxTriggerAgeMinutes": 10,
    "friendStatusMaxAgeMinutes": 15,
    "drawCooldownMinutes": 30,
    "maxDrawsPerUserPerDay": 6,
    "maxReviewsPerDay": 10,
    "skipCooldownDays": 7,
    "errorCooldownMinutes": 60,
    "maxQueueAgeSeconds": 120,
    "scoreThreshold": 70,
    "weights": { "quality": 40, "interest": 30, "reciprocity": 20, "stability": 10 }
  }
}
```

`mode=prompt` 兼容原实现，`mode=triggered` 启用新编排。总开关和 `graduated` 独立保留。
缺少 `mode` 的旧配置迁移到 `triggered`，确保升级后停止普通聊天中的交友提示词注入；
如需回滚，管理员可在好友管理页显式切换到 `prompt`。两条提名路径始终互斥。
正式切换新模式时普通聊天的前缀只变化一次；其后的抽签不能导致频繁 lifecycle rollover。
旧模式尚未结束的工具调用在服务端再次检查当前 mode，新模式下没有有效评估来源不得提名。

实验设置页只放生命周期控制；参数、模式、概率、权重、审计和审批仍归“好友管理”页。
页面需能解释：未达哪条门槛、冷却多久、是否抽签、为何未命中、模型决定及评分、
最终提名和审批结果。停用后依然可看已有记录。

首期不自动根据提名率改概率，不做“多次未中就保底”，也不根据管理员通过率
动态调整某人的权重，避免配置含义漂移。

## 11. 试点验证与研发状态

### 阶段 A：只读数据覆盖率调研（待生产样本）

经授权后在本地/受控副本统计，不调用模型、不通知管理员：

- 当前发言数、活跃天数与直接交流证据的分布。
- 聚批中多人出现的比例；显式 @、引用、续接的占比。
- 好友同步可信度、旧消息关联字段缺失率、可追溯证据比例。
- 不同门槛下预计合格人数和机会量；结果仅汇总，不导出个人聊天明细。

输出决定 50/3/3 是否过严、历史上限是否足够；不要在缺少数据时声称已校准权重。

### 阶段 B：影子试点（可通过概率 0 运行）

与实际两种提名模式互斥的专用试点开关，仅跑本地资格和抽样审计，
不调用模型、不保留旧的自由提名入口，禁止新旧模式叠加放量。
保持入站申请审批、已存在的待审批候选可处理。

建议观察 3 至 7 天，至少收集 100 次合格机会；达不到就延长，不以日期到达视为验证完成。
抽样分布结合样本量解释，不要求小样本观察值恰好等于 5%。
不得重复回放并重新抽样来挑选更好看的分布。

### 阶段 C：受控模型试点（实现完成，待生产启用）

5% 概率，每日最多 3 次评估，保留管理员人工审批，不执行额外真实添加测试。
观察输出有效率、证据正确率、跨群隔离、延迟、Token、管理员驳回原因。
先积累至少 20 次有效评估再调整主观权重；目标不是尽量多加好友。
若直接互动证据缺失，先修复采集，不自动降低安全条件凑样本。

### 阶段 D：正常试点（待阶段 C 验证）

评估通过后可恢复每日 10 次默认预算。支持后台动态切回原模式或完全停用；
切换不删除历史提名、未知发送状态和冷却记录。

已完成研发拆分：

1. 已完成结构化触发证据、受限历史检索及指标口径。
2. 已完成同人限额、持久抽签、配置校验和概率 0 影子模式。
3. 已完成单次模型评估、结果校验和原子提名接线。
4. 已完成好友管理页面、父子 Session 关联和成本统计。
5. 已完成本地回归；生产启用、观察和部署验收尚未执行。

## 12. 验收清单

- 新模式普通请求中没有主动交友指引和提名工具；未命中时无额外模型调用。
- 总开关关闭时无评估请求、无新评估表/索引/任务；已有数据保留。
  首次从旧模式切换的受控前缀变化与之后的稳定行为分开验收。
- p=0 永不命中，p=1 在资格与限额允许时必命中；p=0.05 的边界可确定性测试。
- 多人批次只选正确来源作者中的一人，抽签失败不继续试第二人。
- 已是好友时，即使所有关系门槛达标且 p=1，也不抽签、不检索历史、不调用评估模型；
  评估中途成为好友时取消任务并丢弃迟到结果，正常聊天不受影响。
- 防抖预判、失败重试、批次重组、跨群并发、重启和重复事件不增加抽签机会。
- 普通 50 条发言不能冒充 50 次双向互动；缺失证据不会被昵称或转发内容伪造。
- 未命中只做本地有界统计；历史检索无全库读取，不误带其他群和私聊原文。
- 历史包含注入文本时不能更换目标、提高概率、绕过审批或调用外部发送工具。
- 模型最多一次请求；空输出、错误参数、越界评分、伪造证据、无工具调用均失败关闭。
- 即使达到分数，模型选择 skip 仍不得提名；无有效依据也不得提名。
- 评估失败/超时不影响群聊确认、回复、handoff 或生命周期 transcript。
- 原子提交、管理员通知失败、权限改变、已成好友、入站申请到达等竞态不产生重复申请。
- 停用、切账号、改相关配置立即停止未完成工作，陈旧模型结果不得落库提名。
- 真实发送仍要求管理员批准，未知外部结果不自动重试。
- 控制台展示频控和跳过原因，模型成本只计一次，历史证据按权限和保留期管理。
- 在隔离夹具上验收功能，不为测试擅自向真实第三方发送申请。

## 13. 已采用的关键选择

实现范围是“隔离评估分支 + 每次合格机会 5% + 当前会话历史 +
可配置关系门槛/频控/评分 + 管理员审批”。

50 条、3 活跃天、3 次直接交流和 70 分是待试点校准的建议，不是已经观测验证的事实。
实现和本地验证已完成；影子采集、生产模型试点和生产启用仍未执行。
